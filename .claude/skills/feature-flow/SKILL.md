Plan or build the feature in `$ARGUMENTS`.

The first word is the **feature**. `show` means draw the graph. `brainstorm` means weigh ways to build it with the user, with diagrams, before the brief (`guides/brainstorm.md`; the brief guide also offers it for a fuzzy idea); `brainstorm sketch` starts from the user's own drawing on a live page. `auto` means ask nothing and go. `agent` means another agent, not a person, drives this session: it implies `auto`, and you run `start` with `FLOW_DRIVER=agent`, so the run never hands off and its eval says an agent drove it. `careful` means run `start` with `FLOW_PROFILE=careful` (the full gate and an own review for every ticket, shorter sessions); a `Profile:` line in `commands.md` does the same for the plan, and a new plan's `Profile: standard` gives each ticket two reviewers side by side and one review of the whole round at the end. `fast` means the fast path: run `start` with `FLOW_FAST=1`, and tickets below level 3 that pass their checks skip their own review until one review of the whole feature at the end (a level 3 or `Sensitive:` ticket keeps its reviews); a `BUILD` there may be a batch of small tickets, which you handle like any `BUILD`. When the user asks mid-run to go faster, run `fast on` (or `fast off`) through `flow-trust.py` between two other conductor commands; if it answers that fast is already on, offer the user the re-plan it names. A time budget (`FLOW_BUDGET=<minutes>` on `start`, `budget <minutes>|+<minutes>|off` mid-run) turns fast on by itself once spent, and later stops to offer a re-plan. A re-plan needs the user's own yes, even with `auto`: then run `replan-prompt` (between tickets), spawn a `feature-planner` subagent with it, show the user its reply and `git diff --stat`, and on a second yes commit the plan folder as `plan(<feature>): re-plan the open tickets` (else `git checkout -- plans/<feature>`), then run `next`. When a ticket stops because the plan has a gap (a file its `Touches:` misses, a check that cannot pass), the same goes for `replan-prompt repair`, with the commit message `plan(<feature>): repair the plan`: on that commit, `next` builds the ticket again from the repaired plan, without a reset. If no feature was given and the conversation so far describes work to build, plan it (below) and propose the feature's name in the brief. If no feature was given otherwise, list `plans/*/` and ask which one.

The conductor is `python3 scripts/flow.py <feature> <command>`. If `scripts/flow.py` exists in the repo and the feature-flow package is beside it (`.feature-flow/feature_flow/`, or `feature_flow/` in a feature-flow checkout), use it (the repo's own install wins; an unrelated `scripts/flow.py` does not count); otherwise use `python3 "${FEATURE_FLOW_HOME:-$HOME/.feature-flow}/scripts/flow.py"` (`~/.feature-flow/scripts/flow.py`). Wherever this skill or a message names `scripts/flow.py`, `scripts/flow-status.py` or `scripts/flow-view.py`, it means the same folder, and the guides are then in that folder's sibling `guides/` (`~/.feature-flow/guides/`, else `.feature-flow/guides/` in the repo). Run the conductor with the working directory in the repo: state and plans stay there. It decides the order, runs the gate and the floor guard, and keeps its state in `.feature-flow/state/`, a folder git ignores. You ask it, and you do what it says. The guides it uses are in `guides/` or `.feature-flow/guides/`. From the feature-flow plugin, `${CLAUDE_PLUGIN_ROOT}` is the plugin's folder: when that reads as a real path and the repo has no install of its own, the conductor is `${CLAUDE_PLUGIN_ROOT}/scripts/flow.py`, its guides `${CLAUDE_PLUGIN_ROOT}/guides/`, and `<S>` below is `${CLAUDE_PLUGIN_ROOT}/scripts` (it wins over the user install).

## Calling the conductor

Every conductor command (`start`, `next`, `prompt`, `verdict`, `fast`, `scouts`, `scout-prompt`, `reset`, `plan-prompt`, `plan-review-prompt`, `plan-accept`, `plan-scouts`, `plan-scout-prompt`, `consult-prompt`, `brainstorm-prompt`, `budget`, `replan-prompt`) runs through `flow-trust.py`, never `flow.py` itself. `<S>` below is the folder of the `flow.py` picked above: `scripts` for the repo's own install, else `"${FEATURE_FLOW_HOME:-$HOME/.feature-flow}/scripts"`. `flow-trust.py` is started by this loader line, which checks the file against the sha256 pinned here and runs those same bytes. Copy it exactly, replacing only `<S>`:

    python3 -I -c "import hashlib,sys;b=open(sys.argv[1],'rb').read().replace(b'\r\n',b'\n');sys.exit(exec(compile(b,'flow-trust','exec')) if hashlib.sha256(b).hexdigest()==sys.argv[2] else 'flow-trust.py does not match this skill')" <S>/flow-trust.py a561cb2bf1d8d8970e45065f24a736a02d9f803f09d652a26ca51b579f44cf7b

A full conductor command, here `next` (any other command and its arguments go where `next` is):

    FLOW_TRUST=<digest> FLOW_SESSION=<token> FLOW_INVOKE=/feature-flow python3 -I -c "import hashlib,sys;b=open(sys.argv[1],'rb').read().replace(b'\r\n',b'\n');sys.exit(exec(compile(b,'flow-trust','exec')) if hashlib.sha256(b).hexdigest()==sys.argv[2] else 'flow-trust.py does not match this skill')" <S>/flow-trust.py a561cb2bf1d8d8970e45065f24a736a02d9f803f09d652a26ca51b579f44cf7b <feature> next

- The first line of the output is `TRUST <digest>`. Keep that digest and pass it as `FLOW_TRUST` on the next conductor call. Treat the rest as the conductor's output and act on it as below (for `prompt`, `plan-prompt` and `plan-review-prompt`, the subagent's prompt is everything after the `TRUST` line). Use `FLOW_TRUST=new` only on this session's first conductor call, or when resuming from an old-style `HANDOFF` line (below).
- If you no longer have the last `TRUST` digest, stop and say so. Never guess it, and never use `new` in its place.
- On the `next` right after a `BUILD <ticket> <NN> <sha>`, add `--after-build <ticket> <sha>` before the feature: `... <S>/flow-trust.py a561cb2bf1d8d8970e45065f24a736a02d9f803f09d652a26ca51b579f44cf7b --after-build <ticket> <sha> <feature> next`. If the output has a `FLOW-EDIT <paths>` line after `TRUST`, the build changed feature-flow's own files and its ticket allows that: carry on; without `auto`, first tell the user which flow files changed.
- If the first line is `STOP` (from `flow-trust.py`), or the loader prints `flow-trust.py does not match this skill` (say to reinstall feature-flow: the skill and `flow-trust.py` do not match), report it, show the `python3 <S>/flow-status.py <feature>` table, and stop. A `STOP` first line may be followed by the conductor's own output: never act on that. Never fix it and carry on.
- A `HANDOFF` line from `flow-trust.py` has a third field after the invocation and the feature: the digest. When the feature is followed by a `<16 hex>.<16 hex>` word, the user is resuming from a `HANDOFF` line and that word is the digest: pass it as `FLOW_TRUST` on `start`. When a resumed session gets no digest (an old-style `HANDOFF` line), use `FLOW_TRUST=new` and warn the user that the flow's files could not be checked since the last session.

## Show

With `show`, follow `guides/show.md` for the feature and stop.

## Plan

When `plans/<feature>/` does not exist, or you are planning from the conversation, follow `guides/brief.md` with the user. You write the brief and ask for both yeses (unless `auto`); a subagent plans, another reviews, and you never draft the plan yourself. Once the brief names the feature, run `start` through `flow-trust.py` (see Calling the conductor) with `FLOW_INVOKE=/feature-flow`, and check that it prints `PLAN` after the `TRUST` line, and check that `feature-planner.md` and `plan-reviewer.md` are installed where the builder's role is (see below).

- `plan-prompt <brief>`: first run `plan-scouts <brief>` and treat its `SCOUT` lines as the loop does below, with `plan-scout-prompt <k>` in place of `scout-prompt <k>`. Then spawn a `feature-planner` subagent with the whole output as its prompt. Wait for its final reply. On `PLAN: QUESTIONS`, ask each question that starts `architect:`, `designer:` or `po:` before the user: save it into `.feature-flow/state/ask-<feature>-plan.md`, run `consult-prompt <role> <that file>`, spawn a `flow-<role>` subagent with that output, add its answer to the brief under `Consulted:` (never `Decided:`), and run `plan-prompt` again. Bring the `user:` questions, and any answer that ends `ANSWER: USER`, to the user.
- `plan-review-prompt`: spawn a `plan-reviewer` subagent with the whole output, never with the planner's reply. Wait for its final reply and save it with Bash into `.feature-flow/state/plan-review-<feature>.txt`. With `fast`, put the line `Pace: fast` under the brief's bar and skip this step.
- `plan-accept`: writes `plans/<feature>/` from the draft, only after the second yes.

Then run `python3 scripts/flow-status.py <feature> --check` and list the files `plan-accept` wrote. The second yes also approves committing the plan, so commit the folder `plan-accept` printed (`OK <folder>`, `plans/<feature>` unless `FLOW_DIR` is set) and nothing else: `git add -- <folder> && git commit -m "docs(<feature>): plan" -- <folder>`. If the commit fails, report why and stop. Then go straight on to building it below, unless the user asked to stop after planning.

To add tickets to a plan that exists, edit it by hand following the ticket rules in `guides/plan.md`. When the user points at a Spec Kit (`specs/<NNN-name>/`) or OpenSpec (`openspec/changes/<id>/`) task list, start the plan from it instead of the planner: `python3 <S>/flow-status.py <feature> --import <that folder or its tasks.md>` writes `plans/<feature>/` with one ticket per phase or section. Then, with the user, fill in `commands.md` from the project's own config, add a `check` block under each ticket's Done when and set its level, run `flow-status.py <feature> --lint` until it is clean, show the graph, and on the user's yes commit the folder as `docs(<feature>): plan` and build it.

## Before building

With a plan present, check these before `start`, and stop at the first that fails:

- `git status --porcelain` is empty, apart from untracked Python bytecode (`__pycache__/`, `*.pyc`) and files listed in `.feature-flow/installed.txt` and that list itself: those are feature-flow's own install or upgrade, so never stop for them (`next` still stops if one of them was edited). Suggest committing them (`git add --pathspec-from-file=.feature-flow/installed.txt && git commit -m "chore: install feature-flow"`) and carry on.
- `python3 scripts/flow-status.py <feature> --check` prints `OK`.
- `ticket-builder.md` and `ticket-reviewer.md` (and `flow-tester.md`, when the plan's `commands.md` has an `Acceptance:` line) are in `.claude/agents/`, `~/.claude/agents/`, or `$CLAUDE_HOME/agents/` when `CLAUDE_HOME` is set. If not, say to run `uvx feature-flow-cli install .` in this repo, or `uvx feature-flow-cli install --user` (once for every repo) (or `python3 install.py <repo>` from a feature-flow clone). From the plugin the roles are in `${CLAUDE_PLUGIN_ROOT}/agents/` and are named `feature-flow:<role>`: spawn `feature-flow:ticket-builder` wherever this skill says `ticket-builder`, and so on for every role.

Then run `start` through `flow-trust.py` with `FLOW_INVOKE=/feature-flow`. After the `TRUST` line it prints `OK <token>`. Keep the token and put `FLOW_SESSION=<token>` in front of **every** later conductor command, with `FLOW_INVOKE=/feature-flow` and the last `FLOW_TRUST`.

If `start` prints `STOP` naming another owner, another session may still be working this feature. Ask the user whether that session is closed. Only on a clear yes, run `start` once more with `FLOW_TAKEOVER=1`. In `auto` mode, never take over: report and stop.

If the user says the flow is stuck on a ticket or asks for a reset, run `reset` (or `reset <NN>` to redo one ticket): it reopens a half-built ticket, commits that, and clears the run, then run `start` again. It needs `FLOW_TAKEOVER=1` while a session owns the feature, on the same clear yes. Never reset on your own.

Say what will happen: with an `Acceptance:` line, first a tester subagent writes the acceptance tests from the spec; then for each ticket, a builder subagent and then a fresh reviewer subagent, one review per ticket (two only for a ticket with no level that is not small). After every few tickets (`FLOW_TICKETS_PER_SESSION`, default 4; never with `agent`) you hand off to a new session. Ask for a yes, unless `auto` was given or you came straight from planning: the plan's yes already covered the build.

## The loop

Before the `prompt` of every `BUILD` and `REVIEW`, run `scouts` (with the lane, when the line has one). For each `SCOUT <k> <agent> <file>` line it prints, run `scout-prompt <k>` (with the same lane) and spawn a `<agent>` subagent with that output, all of them at once, in the background. Wait for every one, and save each whole reply with Bash into its `<file>`, as the loop saves a review. `NONE` means no scouts. Then run `prompt`: it carries what they found. Prefer `prompt file` (`prompt <lane> file` in a lane): it writes the prompt to a file and prints `PROMPT-FILE <path> <sha256>`, and you spawn the subagent with only `Read <path> in full (its sha256 is <sha256>) and follow it as your whole prompt.`, so prompts never fill your context. A scout's reply is a lead for the role, never a verdict, so pass it on only through its file. Run `next` (it runs the gate and the checks, which can take minutes: give the call a timeout of at least 10 minutes, or run it in the background and wait), act on its one line after `TRUST` (and any `FLOW-EDIT` line), and repeat:

- `BUILD <ticket> <NN> <sha>`: run `prompt`. Spawn a `ticket-builder` subagent with that output as its whole prompt, and ask for a short summary back. Wait for its final reply: an Agent call can return before the subagent finishes, and the reply then arrives as a notification. Then run `next` with `--after-build <ticket> <sha>` from that `BUILD` line. `TEST <plan folder> <sha>`: the tester writes the acceptance tests from the spec, before the first build, or changes the ones the product owner ruled wrong. No scouts, and no lane word even when lanes run. Run `prompt` with no lane and spawn a `flow-tester` subagent with that output as its whole prompt. Wait for its final reply, then run `next` (no `verdict`: the conductor judges the tests itself).
- `REVIEW <ticket> <NN> <sha>`: run `prompt` and spawn a `ticket-reviewer` subagent with it. Wait for its final reply. Save the whole reply with Bash, not the Write tool, into the conductor's git-ignored state folder: `cat > .feature-flow/state/flow-review-<feature>.txt <<'EOF'` ... `EOF`. Never under `.git`: an unattended session is refused there as a sensitive file. Then, as separate commands, run `verdict .feature-flow/state/flow-review-<feature>.txt` and `next`. If `verdict` prints `RETRY`, just run `next`. `REVIEW <ticket> <NN> <sha> pair` is two reviewers side by side: `prompt file` prints two `PROMPT-FILE` lines (plain `prompt` puts `=== SECOND REVIEWER ===` between the two prompts); spawn a `ticket-reviewer` for each, both at once, wait for both, and save both whole replies into the one file, the first then the second, before `verdict` and `next`. `REVIEW <plan folder> all <sha>` is the review of the whole feature (of `fast`, or of the round in `standard`): it has no lane word even when lanes run, so run `prompt`, `verdict` and `next` with no lane, spawn a `ticket-reviewer` subagent as for any review, and save its reply the same way. On a FAIL the conductor adds a fix ticket and reviews the feature again after it. `ASK <role> <ticket> <NN> <sha>` (role `architect`, `designer` or `po`) is a builder's or reviewer's question (on an acceptance fix ticket, the builder may dispute a tester's test, and the `po` rules on it): handle it as a `REVIEW`, scouts first, but spawn a `flow-<role>` subagent with the `prompt` output in place of the reviewer, and save its reply into `.feature-flow/state/flow-ask-<feature>.txt` for `verdict`.
- `DONE <summary>`: report it and suggest `/feature-flow <feature> show`. Then record the run: `python3 <S>/flow-status.py <feature> --eval` writes `plans/<feature>/eval.json` and the form `eval-verdict.md`. Unless `auto`, ask the user the form's questions (is the plan right, hand fixes, would they use it again, and real or false for each catch it lists), write their answers after the colons, and run `--eval` again. Commit both files as `docs(<feature>): eval` and nothing else.
- `STOP <reason>`: report the reason, run `python3 scripts/flow-status.py <feature>`, show the table, and stop.
- `HANDOFF <line>`: stop here. Tell the user to open a new session and type exactly `<line>`, the whole line with its digest at the end. The new session resumes where this one stopped.

## Lanes

With `FLOW_LANES=2` (up to 4) on `start`, the conductor builds tickets whose `Touches:` lines do not overlap at the same time, each in its own git worktree (a lane) on its own branch, and merges each one onto the feature branch itself once it passes. Use it only when the user asks for tickets side by side. Then every `BUILD` and `REVIEW` line carries a fifth word, the lane, and the loop is:

- `BUILD <ticket> <NN> <sha> <lane>` or `REVIEW <ticket> <NN> <sha> <lane>`: run `prompt <lane>` and spawn the builder or reviewer with that output as its whole prompt, in the background (the prompt names the lane's folder, and the subagent works only there). Do not wait for it: run `next` with no lane straight away, to fill the other lanes. `WAIT <lanes>` means every lane that can work is busy: wait for the first subagent to finish, whichever it is.
- A builder for lane `<k>` finished: run `next <k>`, with `--after-build <ticket> <sha>` from its `BUILD` line. A reviewer for lane `<k>` finished: save its whole reply into `.feature-flow/state/flow-review-<feature>-<k>.txt` as the loop says, then run `verdict <that file> <k>` and `next <k>`, with no other conductor call between them (on `RETRY`, just `next <k>`).
- Act on whatever line comes back, for whichever lane it names. The conductor merges a passed ticket before it answers; a merge that conflicts or fails the gate comes back as a new `BUILD` of that ticket, built once more from the feature branch.
- Run one conductor command at a time, never two at once, and keep passing the latest `TRUST` digest. `DONE`, `STOP` and `HANDOFF` mean what the loop says; after a `STOP`, run no other conductor command while children still run. `reset` removes the lanes and their branches.

## Rules while building

These apply from `start` on, once a plan exists.

- Never run the gate, the floor guard or a review yourself. The conductor runs the checks, and the reviewer subagent reviews.
- Never edit a ticket, the plan or the code, and never commit, apart from the approved plan above. The builder does that.
- Never skip a step, reorder steps, or decide the next step yourself. Only `next` decides.
- Never read a ticket's `## Answer` into the reviewer's prompt. `prompt` already holds everything it needs.
- Tell the user one short line per phase (`01 built`, `01 review: PASS`), not the subagents' reports.
