# 12 — One prompt to build an "advisor-style" agent system

> Transcribed from photos of the original document shared on 2026-11-22. One line
> (the second "kind of unknown" in §3) was not legible in the photos and is marked
> where it occurs; everything else is as written in the original.

How to use: replace the `<<...>>` placeholders in the prompt below, then paste everything
between the two `=====` lines into an AI coding agent that can create files and run commands.
The prompt is domain-neutral. It encodes the architecture of the Walled Garden advisor
(read-only expert skill, source whitelist, graded answers, routing, hand-off, ledger) **plus
the improvements** recommended after reviewing it, which are listed again at the end for
reference.

=====

You are building an **advisor-style agent system**: a read-only expert agent that answers
questions about a body of authoritative files, plus the routing, hand-off, audit and
verification machinery around it. Build it in the repository at `<<REPO_PATH>>`.
Domain: `<<DOMAIN, e.g. "our cloud platform design">>`. Authoritative corpus lives at
`<<CORPUS_PATH>>`. Callers who consume the advisor's answers live at `<<CALLER_WORKSPACE>>`.

Work in this order. Do not skip steps. After each step, run the checks named in it and fix
failures before continuing. Do not invent facts about the corpus: read it.

## 0. Principles (apply to everything you write)

1. **Knowledge in files, behaviour in skills.** The corpus is plain files. The advisor is an
   instruction file. No service, no database.
2. **One owner per fact.** Every rule lives in exactly one file; other files point to it.
   Never copy a rule or a roster into a second place.
3. **Rosters are computed, never typed.** Lists of "what exists" are generated from an index
   file at read time or by a script. Hand-kept lists go stale.
4. **Read-only advisor; separate writers.** The advisor never edits. Changes go through a
   different, human-gated skill.
5. **Grades drive behaviour.** Every claim carries a confidence grade, and downstream steps act
   on the grade.
6. **Mechanical checks beat instructions.** Wherever a rule can be checked by a script, write the
   script and make the workflow depend on it. Use prose rules only for judgement.
7. **Small core, large references.** Keep each skill file short; load references only when the
   question needs them.

## 2. The corpus contract

Write `corpus/README.md` and make the corpus obey it:

- Each source is classified into an **authority tier** (1 highest). Record the tier list in
  `references/sources.md` only.
- Each source file is either **authoritative**, **supporting** (owned by another team; cite as
  such, never as truth), or **excluded** (generated copies, superseded history, binaries).
  Excluded directories are excluded by directory, not by filename.
- Machine-readable resources have stable ids, and `index.json` (generated by
  `tools/build_index.py`) maps id -> file -> section. A resource may reference others by id.
- Prose documents carry anchored, numbered sections so a citation can be verified.
- Provide a **reading guide** for each structured file family (what fields mean). The advisor
  must load the guide before reading that family.
- Ids and section anchors must be stable; if you must rename, record a redirect.

Acceptance: `python tools/build_index.py` runs clean and prints counts.

## 3. The advisor skill (`SKILL.md`, <= 150 lines)

The core file contains only:

1. **Description** with trigger keywords and paraphrase examples.
2. **Activation banner**: first line of every reply, exactly
   `ADVISOR — read-only — mode: <Concise|Standard|Research>`.
   It is a visible cue only; real enforcement is in §6.
3. **Start-of-invocation list**: which references to load, in order (`sources.md`,
   `grading.md`, `pitfalls.md`, `talking-to-human.md`, `modes.md`). Load `modes.md` only for the
   chosen mode.
4. **Workflow** (numbered, short):
   1. Identify the topic and check the question's premise; if the premise is false, say so first.
   2. If a term is ambiguous in a way that changes the answer, state the reading in bold, or ask.
   3. Locate sources through `index.json`; read the actual files; never answer from memory.
   4. Apply the authority ladder; flag undocumented conflicts as findings, never silently pick.
   5. Grade each claim (see below), cite each claim, run the gates.
   6. Answer in the chosen mode.
5. **Hard rules**: read-only; cite every claim; grade every claim; never name an id, key,
   section, or policy statement you have not opened; "talk to the human owner" beats a guess.
6. **Scope boundary**: what the advisor does not answer, and which team to name (a team, never a
   skill, except the single sanctioned hand-off to the curator).

### Grades (put the definitions in `references/grading.md`, not in SKILL.md)

| Grade | Meaning | Caller may build on it? |
|---|---|---|
| Fact | Stated in an authoritative source; cited exactly | yes |
| Derivation | Direct logical consequence of named facts | yes |
| Assumption | Plausible, never stated; flagged | **no** — becomes a human decision |
| Cannot-answer | No confident basis; say so | **no** — becomes a human decision |

Labels that are not extra grades: `Fact (external-doc)`, `Fact (decision-record)`,
`Fact (recorded-proposal)`. They mark weaker provenance.

Two kinds of unknown: **intent gap** (route to the human owner; never guess from outside docs)
[the second kind was not legible in the source photos].

### Gates (each is one short paragraph in `grading.md`)

Premise check; ambiguity surfacing; citation verification; config-value (a value is not intent);
premise sourcing (unsourced premise = Assumption); enforcement semantics (a policy's condition
must actually enforce the claimed control); recorded-proposal (a recommendation is not a fact);
scope/allow-list gate for anything the advisor recommends; external-doc verification.

Acceptance: `SKILL.md` <= 150 lines; every gate defined once, in `grading.md`.

## 4. Routing and activation (`steering/routing.md`)

Write a dispatcher with, for each skill: intent triggers (match on intent, not keywords) and a
one-line boundary. Include this discipline verbatim in spirit:

- **Activation is an action, not a label.** Loading the skill file and emitting its banner is
  activation. Saying "the advisor would say..." is a skipped gate.
- Run a pre-answer self-check: does this touch `<<DOMAIN>>`? If plausibly yes, activate first.
- Bias toward the read-only advisor when unsure.
- Re-activate on every turn that resumes the domain.
- A reply on the advisor's matter is either the advisor's own reply (banner first) or a verbatim
  relay. A paraphrase is not the advisor's reply and must say so.
- A closed list of trusted skills; skills cooperate only within it.

Add a **fast path**: a short list of low-risk question types (single-fact lookups) that may use
Concise mode and skip the full gate set, but never skip citation verification.

## 5. Curator and governor

- **Curator**: writes only the corpus targets it lists; every change needs human confirmation;
  lands as an atomic, signed commit; runs the validators first; consults the advisor for any
  interpretation question before editing.
- **Governor**: writes only skill definitions, routing, governance hooks and tests (never its own
  definition); runs `check_skill_drift.py`; each new rule must name its single owner file and be
  covered by a check or an eval.

## 6. Mechanical verification (build these scripts; they are the real guardrails)

1. `tools/verify_citations.py <reply.md>` — parse the reply's citations (file path, section
   anchor, resource id, policy/statement id) and confirm each exists in the corpus/index. For
   quoted text, confirm the quote appears in the cited file. Exit non-zero listing failures.
2. `tools/check_banner_and_format.py <reply.md>` — first line equals the banner; every claim line
   carries a grade; sources list present; no forbidden source paths cited.
3. `tools/build_index.py --check` — fails if `index.json` is out of date.
4. Make the caller workflow (§7) **refuse to ledger a reply** unless both reply checks pass.
   The banner alone is never accepted as proof.

## 7. Caller side (what the consumer workspace needs)

The advisor lives in its own workspace; callers reach it by **hand-off**:

1. `caller/skills/ask-advisor/SKILL.md`: start a fresh sub-session with the advisor workspace as
   its working directory, load the advisor, send a prompt, return the reply **verbatim**.
2. Three prompt templates, each ending with a required output table:
   - **briefing** (before building anything): per item, answer a fixed question list
     (class, scope, origin, identity, expected outcome, path, source), graded and cited;
   - **review** (after building): "try to break it"; report agree / defect / cannot-answer per
     item, with the fix the design calls for;
   - **grading** (after execution): classify each failure as real / by-design / spec defect /
     plan defect / inconclusive, with citations.
3. Pass data **by file, not by paste**: the caller writes a structured input file
   (`inputs/<n>.json`) and the sub-session reads it. This prevents truncation and dropped rows.
4. **Ledger** (`ledger-template.md`, one per piece of work): columns item, step, answer fields,
   grade, citation, source reply file, status
   (`grounded | defect | open:<grade> | override:<who, when> | unverified:<error>`).
   An item with no `grounded` row is not built. `unverified` blocks completion and any run.
   `open` rows go to a human as a decision (context, up to three options, one recommended).
5. Saved replies are never edited by the caller.

## 8. Evaluation (build before declaring done)

- `evals/golden.jsonl`: at least 30 questions with expected graded answers and required
  citations, covering: simple facts, conflicts between sources, false premises, ambiguous terms,
  out-of-scope services/actions, intent-gap questions (must yield Cannot-answer), and
  external-platform questions.
- `evals/run_evals.py`: runs each question through a fresh advisor session, applies
  `verify_citations.py` and `check_banner_and_format.py`, compares grade and key facts, prints a
  pass/fail table and a drift score.
- Run the evals after any change to a skill, a reference, or the corpus. The governor refuses a
  skill change that lowers the pass rate.
- Run each eval three times and flag questions whose grade changes between runs.

## 9. Anti-drift checks

`tools/check_skill_drift.py`: fail when (a) a rule sentence appears in two skill files,
(b) a roster is hard-coded instead of generated, (c) a reference is cited but missing,
(d) `SKILL.md` exceeds its line budget, (e) a rule lacks a named owner.

## 10. Documentation

Write `docs/architecture.md` with Mermaid diagrams: (1) system overview, (2) one advisor
session, (3) hand-off sequence, (4) authority ladder, (5) verification pipeline. State clearly
what is checked by scripts and what depends on model judgement.

## 11. Definition of done

- All scripts run; `evals` pass at or above the threshold you record in `evals/README.md`.
- A worked example: a sample question flows caller -> hand-off -> advisor -> verify scripts ->
  ledger, with the saved artefacts shown.
- `SKILL.md` <= 150 lines; no rule duplicated; no hand-typed roster.
- A summary that lists what you built, what you could not verify, and what depends on the model
  rather than on a check.

## 12. Recommended improvements (implement all of these; each is already built into the steps above)

1. **Verify by script, not by banner.** `verify_citations.py` and `check_banner_and_format.py`
   gate the ledger. (§6)
2. **Small core, loaded references.** Core skill <= 150 lines; load only the references the
   question needs; mode rendering rules loaded per mode. (§1, §3)
3. **Golden-question evals with repeat runs** to catch drift and run-to-run disagreement. (§8)
4. **Hand off by file, not by paste**, so cases are not truncated or dropped. (§7)
5. **A fast path** for low-risk lookups so the process cost matches the risk. (§4)
6. **Drift checker** so a rule has one owner and rosters are generated. (§9)
7. **Grades that change behaviour:** Assumption and Cannot-answer become explicit human
   decisions, never silent assumptions. (§3, §7)
8. **Record sheet-vs-design conflicts as structured data** (a table the ledger exports), not only
   prose notes, so they can be queried and re-checked later. (§7)
