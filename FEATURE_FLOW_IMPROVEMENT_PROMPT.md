# Prompt: improve FeatureFlow reliability, speed, and recovery

Investigate and improve FeatureFlow using the portable-live-page run as a concrete case study. Read the current code and tests first, reproduce each issue where possible, distinguish confirmed defects from operator error, and propose or implement prioritized fixes. Preserve review independence, approval intent, and protection against unsafe state changes.

## Observed problems

1. A trust call used an older digest after a successful `next`; the loader reported that flow files changed, while its saved per-file list named no changes. The actual error was my failure to carry the latest returned digest. Make the current token hard to lose, report stale tokens distinctly when possible, and give an explicit safe diagnostic/recovery path without weakening change detection.
2. A plan repair was necessary because ticket 03 needed two files outside `Touches:`; only one extra file was allowed. The user approved repair. The repair planner widened the proposed footprint, but lint reported pre-existing warnings in resolved ticket 02, which the planner was forbidden to change. A later `consult-prompt architect` returned `STOP ... already exists` because the consultation followed a path intended for creating a new plan. Reproduce and fix repair-mode consultations for existing plans; baseline inherited warnings, report ownership and severity, and allow a scoped repair to finish without silently suppressing new warnings or rewriting resolved history.
3. Fast mode rejected a documented one-file footprint exception although normal mode accepted the same declaration. Make mode-dependent rules explicit before work starts, keep behavior consistent where safe, and offer a reversible switch or repair with actionable diagnostics.
4. The browser suite passed but a ticket check expected literal TAP `# fail 0`, while the installed Node default reporter emitted `ℹ fail 0`. Prefer stable machine-readable results or explicit reporter configuration, with clear setup checks; never weaken a check to hide failures.
5. Each rebuild repeatedly ran a long test-first historical suite and the complete gate, taking roughly 14 minutes even for small follow-up fixes. Explore safe caching keyed by exact commit, commands, dependencies, environment and relevant inputs; reuse only verified immutable results, invalidate deterministically, and run risk-appropriate focused checks early. Measure end-to-end elapsed time, cache hit rate and false-reuse risks. Preserve a complete final gate and independent review.
6. Review repeatedly found related asynchronous data-loss cases (typed draft cleared after an earlier save; pending choice cleared after approval; stale operation blocking the queue). Improve review and test design around operation lifecycle, concurrency, recovery, and adjacent variants; group related findings when possible so a single repair addresses the whole class. Do not claim a review guarantees absence of defects.
7. Review prompts referred to historical ticket blobs that already contained author Answers, exposing reviewers to claims they were instructed not to read. Generate immutable reviewer inputs that structurally exclude Answers and author proof, including appended review material, and test that isolation.
8. Long-running gates produced little actionable progress and encouraged repetitive status updates. Emit structured phase, elapsed time, last-progress and expected next-step information; distinguish running, stalled, failed and complete without leaking sensitive data.
9. Resumption after a STOP required manual reconstruction of a trust digest, owner, phase and repair context. Design a durable, inspectable state machine with idempotent transitions, atomic checkpoints, explicit ownership and safe takeover, crash recovery, precise commands to resume, and a dry-run diagnosis. Never reset, discard work, or accept changed code silently.
10. The workflow could not reconcile a verified repair requiring multiple files outside the footprint without a multi-stage manual stop. Provide a reviewable scope-repair proposal that records evidence, affected files, tests and dependency impact, preserves completed work, and requests only the approvals actually required.

## Requested deliverables

- A prioritized root-cause report with severity, evidence, reproducible cases, and which issues were tool defects versus operator mistakes.
- A design and phased implementation plan covering trust, plan repair, state and ownership, build/review isolation, acceptance tests, security, cross-platform behavior, observability, packaging, upgrades, documentation and usability.
- A separate performance proposal with measured baseline and target timings for small fixes, normal tickets and full features; identify mandatory checks, safe parallelism, cache boundaries, cancellation and invalidation. Include a benchmark and failure-injection plan rather than arbitrary speed promises.
- A separate recovery proposal showing the exact user experience for stale tokens, changed files, crashed agents, failed gates, stopped consults, plan gaps and session handoffs. Include concrete commands/messages and preservation of uncommitted work, pending reviews and approvals.
- Acceptance criteria and regression tests for every proposed change, including concurrency, interrupted writes, stale caches, malicious or corrupted state, and upgrades. Explain tradeoffs and migration risks.

Do not assume this case proves every possible FeatureFlow weakness. Validate claims against the current repository and report uncertainties. Do not change approval rules, skip reviews, or bypass trust checks merely to improve speed.
